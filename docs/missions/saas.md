# SaaS product missions

These are two coherent application builds, not collections of independent validators. Both contain eight substantial workstreams and one shared product goal. A solo participant must complete the same goal as a two-, four-, or eight-person implementation. Workstream assignments change who focuses on a feature; they do not remove product requirements or reserve files.

**Operations Desk** covers tenant authorization, incident lifecycle, transactional persistence, incident operations, audit, search and reporting, accessible workspace rendering, and application integration. The shared lifecycle runs from open through triage and mitigation to resolution; administrative reopening and cross-incident linking exercise longer workflows. Comments, ownership, severity reporting, resolution times and user-facing controls must all agree with the persisted records.

**Reservation Ledger** covers tenant/customer authorization, scheduling, persistence, reservations, billing, audit and reporting, accessible workspace rendering, and application integration. Holds and confirmations consume interval capacity. Payments, partial refunds, cancellation, replay and capacity release share one atomic store. Customers can see their own reservations; tenant staff see their tenant; administrators have refund authority. Payments are simulated ledger entries, with no external financial effects.

Each seeded workspace has eight editable modules, an editable stylesheet and README, and protected product instructions, versioned schema metadata, example data and a Node ES-module manifest. Every module initially throws `Not implemented`. No reference solution or expected evaluation responses are seeded. The fixture goals are approximately 5–6 KiB, and each workstream brief stays under 1.2 KiB. Dependencies point to the producer and consumer module paths. See `PRODUCT.md` in a seeded workspace for the full public API and error contract.

The integration API is `app.mjs` → `runScenario({seed,initial,tenantID,actorID,timeBase,commands})`. It returns ordered command responses, an authoritative private persistence snapshot, scoped analytics and rendered HTML. The snapshot is a trusted simulation/evaluation channel, not a customer-facing API response. Commands can be replayed, batched concurrently, denied, rolled back or applied after a repository reload. User-visible records, analytics, audit responses and HTML have their own tenant/customer visibility boundary.

The trusted parent grader creates fresh scenario IDs and escaped-text probes. The reservation grader also varies time windows and resource rates, so implementations must compute from supplied data. Assertions remain outside submission code. Invocations run only submission modules in the bounded child provided by the common verifier; the parent examines their JSON responses and state. Operations uses eleven child invocations and fourteen named criteria; reservations uses fifteen invocations and fifteen named criteria, within the common sixteen-call/thirty-second budget.

The graders examine domain transitions, durable replay and conflicting request bodies, optimistic concurrent writes, rollback, non-disclosing authorization, analytics, reference integrity, billing bounds and interval capacity. Required-behavior checks remain separate from protected-file/scope instruction checks. Successful mutations must have matching audit revisions; replay and failed commands must not create orphan state or audit records.

UI checks inspect actual rendered data with generated values, escaped hostile markup, labelled enabled inputs, submit buttons, form action/method and bound operation/record fields. They route values from a rendered form back through the application API and verify the resulting state and render. These are structural and semantic workflow checks, not screenshot, contrast, browser-layout or comprehensive accessibility certification. A human reviewer should assess coherence, usability and visual quality separately.

Each fixture supplies a public, author-neutral `reviewInvocation`. It runs ordinary representative product actions using the protected example seed and returns a visible workspace with realistic records. It contains inputs only, no expected responses or scores. Use the same invocation for every configuration. Present its sandboxed, network-disabled HTML and JSON before disclosing implementation identity, elapsed time, model allocation, cost or automated grades. Source files can be inspected without provider/team branding. The reference implementation exists only in deterministic tests.

Deterministic tests prove that the original skeletons fail, complete test-only references pass, and selected serious faults are caught: cross-tenant authorization, unsafe HTML rendering, unlimited capacity and over-refunding. This finite scenario suite does not establish production security, database durability under process failure, payment compliance or product superiority.
